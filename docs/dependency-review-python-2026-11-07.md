# Python and backend toolchain dependency review (2026-11-07)

This review covers every Python version change in the original nine-file staged update, the newly introduced Python transitive dependency and the backend runtime/tool updates. The baseline is commit `0475d873047c876b16c78f428ecb59dea0723e98`, the reviewed staged `pyproject.toml` blob is `1788504c4dc84a5fd117997674093a24852bacdd` and the reviewed staged `uv.lock` blob is `8c67fe5570c6f8d5997352656bf445bb90ed123d`. Later removal of the coverage tooling is a separate user-requested change, not an upstream compatibility requirement.  
Versions below are exact resolved versions from `git show HEAD:uv.lock` and `git show :uv.lock`, not just the compatible-release bounds in the manifest. There are 18 changed direct Python dependencies, one changed transitive package, one new transitive package and three backend tools/runtime records. The existing `.venv` matched all target Python package versions when inspected. Upstream sources were read on 2026-11-07, conclusions apply to this snapshot rather than all future compatible releases.

CI preserves `uv sync --frozen --extra dev,local`, whose comma-separated extras were verified with a successful dry run under uv 0.13.7. The lockfiles still freeze application dependencies, tool/base-image versions may vary on a later fresh bootstrap. No current container run is implied.

## Cross-Interpreter Follow-up

The initial schema mismatch was not a FastAPI package regression: with the same dependencies, Python 3.12's `http.client.responses[422]` supplies `Unprocessable Entity` while Python 3.14 supplies `Unprocessable Content`. Existing custom 422 maps now explicitly declare `Unprocessable Content`, preserving one deterministic schema/client snapshot on both interpreters. A regression mutates the standard-library status phrase and verifies exported descriptions remain stable, built-in FastAPI `Validation Error` descriptions are unchanged. Three local-readiness success tests now exercise both optional-dependency presence states without importing/downloading an ML model, so the documented dev-only install can run the suite without the heavyweight local extra.

## Applied compatibility changes and verification

The implementation changes are limited to SQLAlchemy/type annotation compatibility in seven backend files and one new SDK boundary test in `tests/test_ai_providers.py`. Runtime provider selection, retry policy, redaction policy, transaction boundaries and database schema were not changed. No Git index writes, commits, service changes, real Telegram/OIDC/provider requests or credential reads were performed by this audit.  
All test evidence below uses Windows x86-64 CPython 3.14.7 from the existing uv-managed `.venv`, not Docker's Python 3.12. Each pytest run used a fresh external basetemp directory. The full suite, CLI/OpenAPI gates and container acceptance are owned by the orchestrator and must not be inferred from these focused results.
