# Independent AI routes, local inference and embedding migrations
Status: implemented following the owner's instruction to proceed without further design/review approval stops, offline and isolated OpenAI acceptance recorded in [the verification record](../../mixed-provider-acceptance-2026-11-07.md), deployment/live-group acceptance remains open. Baseline: clean commit `b19244d` on 2026-11-07.  
## Intent and approved scope
The owner wants any supported provider to serve answers or summaries independently, including fully local text generation, and wants future embedding-model changes to work without corrupting retrieval. They selected both direct Hugging Face inference and local model servers. OpenAI live acceptance may use their existing key, DeepSeek has no supplied key, and later integration checks may use the existing `test pzp-ai` Telegram group. No Git mutations are authorized. Preserve the owner's CI lock-check removal and Docker pnpm installer policy.  
## Approaches and decisions
- Local execution: support both an embedded Hugging Face backend and an explicitly local OpenAI-compatible server profile. The owner selected both, local servers are the preferred operational choice for larger models, embedded inference covers single-device CPU/GPU deployments without another server
- Operation routing: extend the existing profiles and scoped settings with independent chat, summary and embedding routes, rather than inventing separate credentials/configuration systems for each operation. Existing `provider_profile` remains a backward-compatible fallback
- Embedding changes: build a second index in resumable batches, validate it and explicitly activate it while retaining the old index. Immediate in-place replacement risks mixed spaces and loses rollback, implicit query-time re-embedding creates unbounded request latency and cost, neither is selected
## Goals and non-goals
Support OpenAI-compatible remote services (including DeepSeek), local compatible servers (including Ollama/vLLM/llama.cpp-compatible endpoints) and direct Hugging Face causal-language-model generation for both answers and summaries. Support independently selected local or remote embeddings for every content-producing and query path. Keep settings reloadless where they are currently reloadless, with explicit compatibility/readiness validation and secret-safe observability.  
This pass does not implement training/fine-tuning, arbitrary model repository code execution, multi-GPU embedded sharding, arbitrary remote job execution, a new vector database, automatic cross-vendor fallback, multimedia generation or an inference-server installer/process manager. A configured local server must already be running. Multiple keys within a remote profile retain the existing credential-pool behavior.  
## Independent route contract
Add nullable scoped `chat_provider_profile`, `summary_provider_profile` and `embedding_provider_profile`, with matching safe runtime/environment defaults. Existing `chat_model`, `summary_model`, `embedding_model` and `reasoning_level` remain recognizable. Resolution keeps application/runtime/global/chat/topic/one-shot precedence. An explicit operation profile defaults its model to that profile's model, unless that operation has an explicit model override, it must not inherit an unrelated vendor's model from the old global profile. A null scoped route/model clears the override and restores parent resolution.  
`provider_profile` remains the fallback only when the corresponding operation route is unset. Existing installations with no new settings retain their selected routes/models until explicitly changed. A profile change introduces a model-default boundary: use a model override at the same or a higher precedence layer, otherwise use the newly selected profile's model, never carry a lower-layer OpenAI model into a newly selected DeepSeek/local route. Keep model-origin information so inherited/default/reset values shown in the UI describe that actual resolution. Query-specific `chat_provider_profile` and `retrieval_provider_profile` options remain supported, `retrieval_provider_profile` names the embedding route for that query. Summary one-shot `provider`/`model` options affect the summary text call only, persisted summary embeddings use the configured embedding route. Ordinary chat-model changes do not trigger an embedding rebuild.  
The chat route serves Ask answers. The summary route serves pending/idle/range/manual summaries, knowledge refresh and canonical compaction. The embedding route serves message ingestion, manual/imported notes, summaries, approved reviews, edits/refreshes, re-indexing and search/Ask query vectors. Every path, including startup canonical reconciliation and imports, must use the same centralized operation resolver. Capability validation rejects an embedding-only profile for text generation and a chat-only profile for embeddings. Unsupported reasoning effort is not advertised or sent, telemetry distinguishes requested from effective effort.  
Extend environment/profile parsing, persisted models, migration, repository effective settings, runtime validation, Telegram/CLI argument parsing, centralized formatters, control-plane schemas/OpenAPI/types, settings/catalog/UI and tests together. Profile deletion/disable/model edits must not silently break an active index or pending migration, return an actionable dependency conflict or an explicit unavailable state with no remote fallback.  
## Provider profiles and request compatibility
Retain `fake`, `openai_compatible` and `local` provider kinds. `local` gains separately configured embedded text and embedding backends, either capability can be disabled. An `openai_compatible` profile can be explicitly marked as a local server. Replace the current blanket exclusion of local profiles from chat capabilities, derive actual capabilities from configured backends. Unused model fields need not contain placeholder model names for a disabled capability, construction validates only the requested operation and never requires an unrelated embedding credential to construct a chat-only route.  
Add a small typed request dialect (`auto`, `openai`, `deepseek`, `generic`) rather than arbitrary request JSON. Preserve established OpenAI behavior while recognizing the owner's current GPT-6 identifiers, DeepSeek uses its documented thinking/effort controls, generic/local endpoints receive supported standard Chat Completions fields without OpenAI-only reasoning assumptions. Endpoint/model capabilities remain explicit and testable, unsupported options fail validation or are omitted with the effective policy visible.  
Remote profiles require credentials and retain redaction at the outbound boundary, retry/failover, timeout and safe telemetry. Local server profiles support explicit no-auth operation without inventing stored credentials, and may also use a configured real key when the server requires one. Never inherit the remote default key into a no-auth local profile. A transport-only placeholder required by an SDK must never become a credential-pool entry or be treated as a real key.  
Local-server HTTP is allowed only for an operator-allowlisted local inference origin, including explicit Docker host/container origins, not an arbitrary URL switched to `local=true` by a scoped admin. Reuse bot-owner authorization for provider endpoint/model edits. Reject URL credentials/fragments, forbid redirects and do not expose the local server publicly through Caddy. Host/deployment configuration owns the allowlist, ordinary chat admins may choose only already-configured permitted profiles. A local-only route never falls back to a cloud endpoint.  
## Direct Hugging Face inference
Use the installed Transformers/PyTorch and Sentence Transformers families as optional local dependencies, declare packages directly when the adapter imports them. Target the current locked versions unless a demonstrated compatibility issue requires a separately reviewed update. Do not add heavyweight local dependencies to the default remote-only runtime.  
Expose validated settings for text model ID/local path, pinned revision, tokenizer revision, single device (`auto`, `cpu`, available `cuda` device), dtype (`auto`, `float32`, `float16`, `bfloat16`), cache directory, local-files-only mode, context/output caps, temperature/top-p and bounded inference concurrency. Embedded chat uses a model-supplied chat template, `AutoModelForCausalLM`, inference mode and generated-token-only decoding, a missing/incompatible chat template is an actionable configuration error rather than guessed prompt formatting. Do not silently truncate away instructions or answer context, reject oversized prompts with safe limits. Explicit unsupported devices/dtypes fail clearly.  
Keep `trust_remote_code=False` and safe model weights, do not expose arbitrary loader/model kwargs or an unrestricted remote-code toggle in the UI. Local model/cache paths must remain within deployment-configured model/cache roots, Hub credentials come only from deployment secrets or a secret reference (never the remote OpenAI default key). Loading is lazy and protected against duplicate concurrent loads. Run blocking work off the event loop, serialize generation per model by default, bound queue admission and token generation, support cooperative generation cancellation and account for worker completion before releasing its concurrency slot. Cache model instances by all load-affecting settings, with a deployment-level resident-model limit and idle eviction, release retired instances after in-flight calls finish and close them on application shutdown. No fake success placeholder for unavailable local chat is permitted.  
Embedding controls include model/path, revision, device, cache/local-files-only, batch size, normalization, truncation dimensions and query/document prompt mode. Use query/document-specific encoding where the model defines it, default existing generic MiniLM profiles to the compatible generic behavior. Distinguish dependency presence, model cached/loadable, model loaded and successful inference in readiness, diagnostics must not download models or execute inference merely to display a page. Local-only mode prohibits network downloads, one explicitly initiated preparation step may fetch a model into its configured cache.  
## Embedding-space identity and legacy data
Introduce a persisted embedding-space manifest and foreign key on vector rows. Space identity covers provider/backend kind, normalized endpoint or local model identity, model/revision (including an operator-controlled revision for mutable remote aliases), output dimensions, normalization/truncation, redaction/preprocessing and query/document prompt policy. Credentials, key rotation, cache location and equivalent device choices do not change semantic space identity. Never identify space only by provider type, profile display name, model string or equal vector length.  
Resolve/validate dimensions before declaring a space ready, through existing model metadata or an explicitly authorized bounded preparation call. Store a safe configuration fingerprint, no secrets or raw content. Every embedding result must have the expected count, finite numeric values, consistent/non-empty dimensions and the manifest's dimension. Vector uniqueness is per target and space, retries are idempotent, different spaces can coexist without duplicate retrieval results.  
Existing vector rows have insufficient endpoint/revision provenance. Schema upgrade marks them `legacy_unverified` rather than silently asserting they belong to the current profile. A bot owner can explicitly adopt a previewed legacy mapping when its original provenance is known, otherwise re-index from authoritative stored text. An unverifiable legacy index must never be compared against a new query vector. This can require an explicit post-upgrade re-index before old memory is queryable, show that requirement clearly and preserve the old rows for recovery.  
## Source freshness, queries and scope hierarchy
Each indexed vector carries the fingerprint/version of its authoritative source text. Query eligibility requires a live, permitted source and a matching fingerprint, deleted or edited content cannot remain searchable through an old vector. Index queries filter by exact embedding space before durable-first candidate limits and batched source hydration. No unfiltered or wrong-dimension fallback and no auto-generation from unrelated zero-score context.  
A query uses its selected embedding space consistently across its authorized source scopes. A chat query can include topics with different configured embedding routes, and a memory profile can span chats, but all those sources must also have current coverage in the query's selected space. Otherwise return an explicit coverage/migration-required result identifying safe scope/count information, do not compare raw scores across different spaces or silently omit incompatible topics. Re-indexing can populate additional spaces for a selected hierarchy without changing that hierarchy's active write route. This preserves explicit query-provider choices while making their coverage requirement visible.  
Retained rollback indices are not promised to remain current automatically after activation. Their freshness is computed against current source fingerprints, rollback activation requires rebuilding any missing/stale coverage first. A deleted/forgotten source removes vectors across every space, and in-flight jobs must re-check source existence/content before committing so they cannot resurrect forgotten content.  
## Resumable migration and atomic activation
Persist migration jobs with scope, target route/space fingerprint, initiating actor, expected configuration version, status, bounded cursor/progress/counts, lease/fencing metadata and classified failures. Store source identifiers/fingerprints, not copies of source text or prompts. States distinguish queued, running, ready, failed, cancelled and activated. A supervised worker processes one job at a time in bounded batches, provider calls occur outside database transactions. Resume/restart reclaim uses persisted leases, duplicate workers cannot overwrite one another's progress and cancelled jobs cannot activate.  
The dry-run/prepare view reports eligible message/knowledge counts, existing coverage, expected batches, whether provider use can cost money and whether a local model needs preparation. Starting a job is explicit, profile/model edits create a new target rather than changing an in-flight job's identity. Jobs continually reconcile new/edited/deleted sources, failed batches leave the active index usable and can resume without repeating committed work.  
Use a small persisted global embedding-routing epoch as the cross-process commit fence (conservative invalidation is acceptable because route changes are rare). Each content-producing operation captures the route epoch with its resolved embedding selection, computes embeddings outside the transaction, then acquires a write guard with a compare-and-set on that epoch before committing source plus vectors. If the epoch changed, roll back and retry the embedding step against the new route with a bounded retry count, never commit a newly indexed source only in a retired space. Summary content already generated from unchanged claimed sources can be reused, do not repeat the text-model request just because the embedding route changed. Existing source-version/claim checks remain independent requirements.  
Activation obtains the same durable write guard in one short transaction, validates the current expected scope/settings/profile versions and complete current coverage, updates the selected embedding-route binding/settings and advances the epoch atomically. Missing/stale vectors, deleted profiles, changed source/configuration or lost job fencing abort activation without changing the active route. No network/model work occurs in that transaction. Old in-flight writers therefore either commit before the coverage check or detect the changed epoch and retry afterward. New source scopes also obey the global epoch.  
Re-index-only jobs may become ready without activating a route, useful for query-specific spaces or rollback. Activation must explicitly identify which inheriting scopes/settings are affected, preserve descendant overrides and reject a plan whose version/dependency snapshot changed. Plain runtime/Telegram/CLI/API edits that would change a populated scope's embedding space return migration-required rather than bypassing this workflow. Empty scopes can establish their first space through the same validated binding path without a bulk rebuild.
